1. Executive Summary

The repository is in good shape: pinned chart versions, no :latest tags, resource requests on every deployment, secrets externalized to AWS Secrets Manager, ADRs, and a clean multi-source ApplicationSet pattern. The cluster, however, is in a severe degraded state, and has been for roughly 7 days:

  • Cluster DNS is hard down. The single CoreDNS replica is in CrashLoopBackOff (1,749 restarts) because the Corefile checked into this repo is syntactically invalid for the forward plugin.
  • Everything downstream of DNS is failing: Longhorn CSI volume mounts, all three CloudNativePG clusters, linkding, mealie, miniflux, jellyseerr, bazarr, all 12 ExternalSecrets, and — critically — ArgoCD itself cannot fetch from GitHub or reach its own repo-server, so the GitOps self-heal loop is inside the blast radius and cannot fix anything.
  • The broken config sat dormant since 2026-01-25 (commit 35fa6a7): CoreDNS's reload plugin rejects an invalid Corefile while running, so nothing failed until the pod restarted ~7 days ago and could no longer start. The monitoring stack did not surface this for a week — an alerting gap as significant as the bug itself.
  • Independent of DNS: the Tekton EventListener has been crashlooping for 43 days on missing RBAC (20,898 restarts), Longhorn's "S3 backup" documented in the README is not actually configured (BackupTarget URL empty, unavailable), one Longhorn volume is degraded, and a conveyor-system controller is running in the cluster with no trace in Git.

Bottom line: one invalid line in core-components/coredns/manifests/coredns-custom.yaml took down half the platform, and the recovery path requires manual intervention because GitOps cannot deploy its own fix while DNS is down. Fix order matters — see Remediation Plan.

A second, structural problem makes this worse: the repo overwrites the coredns ConfigMap that k3s itself manages. The live object carries both argocd.argoproj.io/tracking-id and objectset.rio.cattle.io/owner-gvk: k3s.cattle.io/v1, Kind=Addon — two controllers claiming ownership. Any k3s service restart/upgrade re-applies the bundled manifest, ArgoCD self-heal stomps it back. Even after fixing the syntax, this tug-of-war remains. (k3s's supported coredns-custom override ConfigMap doesn't exist in this cluster, and it can't cleanly replace the forward directive anyway, since the import lands inside the existing server block.)

3. Critical Findings

Critical C1 — Invalid CoreDNS Corefile: cluster DNS down ~7 days

core-components/coredns/manifests/coredns-custom.yaml:25 uses a DNS hostname in forward, which only accepts IPs or a resolv.conf path. Even if it were legal, it's a chicken-and-egg: CoreDNS would need DNS to resolve its own upstream.

Fix: Pin a static ClusterIP on the dnscrypt-proxy Service (it currently holds 10.43.24.76 — add spec.clusterIP: 10.43.24.76 to core-components/dnscrypt-proxy/manifests/02-service.yaml) and change the Corefile to forward . 10.43.24.76. Consider forward . 10.43.24.76 /etc/resolv.conf-style fallback thinking: if dnscrypt-proxy is ever down, all external DNS dies again — dnscrypt-proxy is now a tier-0 dependency.
Recovery order matters: fix Git first, then manually patch the live ConfigMap and delete the CoreDNS pod (ArgoCD cannot pull the fix while DNS is down). Otherwise self-heal will keep re-breaking any manual fix.

Critical C2 — Fighting k3s over the coredns ConfigMap

ArgoCD (selfHeal) and the k3s addon controller both own kube-system/coredns. k3s reverts the CM on restart/upgrade; ArgoCD stomps it back. This is why the bad config "worked" for four months and then detonated — the failure mode is non-deterministic by design.

Fix: Own CoreDNS properly: add --disable coredns (or disable: [coredns] in /etc/rancher/k3s/config.yaml) on the servers and deploy the full CoreDNS (Deployment + Service at 10.43.0.10 + ConfigMap, ≥2 replicas) from this repo. That makes Git the single source of truth, which is the project's stated philosophy. Until then, expect drift.

Critical C3 — GitOps control loop has no escape hatch

ArgoCD's repo-server resolves github.com via cluster DNS. With CoreDNS down, the cluster cannot reconcile any change — including the one that fixes DNS. A 7-day outage with auto-sync + prune + selfHeal enabled on everything and no functioning reconciliation is the worst of both worlds.

Fix: Treat DNS as tier-0: run ≥2 CoreDNS replicas with a PodDisruptionBudget and pin pods to different nodes. Add a Prometheus alert on coredns availability and on ArgoCD app Unknown/ComparisonError conditions so a regression pages you within minutes, not weeks.

Critical C4 — No storage backups despite documented "S3 backup"

The README/CLAUDE.md claim Longhorn has S3 backup, but the live BackupTarget has an empty URL and AVAILABLE=false, and no backup settings exist in core-components/longhorn-system/values.yaml. All three PostgreSQL clusters run instances: 1 with single Longhorn volumes; one volume (pvc-c3cc9891, node4) is already degraded and one (pvc-cc64ea92, linkding's DB) is detached/unknown. A single disk failure currently means data loss for bookmarks, recipes, and RSS state.

Fix: Configure defaultSettings.backupTarget (+ credential secret via ExternalSecret) in the Longhorn values, add a RecurringJob for snapshots/backups, and consider CNPG's native barmanObjectStore backups for the databases. Verify the degraded volume rebuilds once DNS is restored.

4. High Findings

High H1 — Tekton EventListener crashlooping 43 days: missing RBAC (20,898 restarts)

applications/tekton-pipelines/manifests/01-rbac.yaml grants the tekton-ci SA access to eventlisteners, triggerbindings, triggertemplates only. The EventListener pod also needs triggers and interceptors (namespaced) plus clusterinterceptors and clustertriggerbindings (cluster-scoped — a Role can't grant these). The CI webhook path has therefore never worked in its current form.

Fix: Bind the SA to the Tekton-shipped aggregated roles: RoleBinding → ClusterRole tekton-triggers-eventlistener-roles, plus ClusterRoleBinding → ClusterRole tekton-triggers-eventlistener-clusterroles. This is the upstream-documented pattern.

High H2 — Unmanaged workload: conveyor-system bypasses GitOps

Namespace conveyor-system (labels: managed-by: kustomize, kubectl.kubernetes.io/last-applied-configuration present) runs conveyor-controller-manager, deployed 52 days ago via kubectl apply. It exists nowhere in this repository — violating the repo's own "Git is the single source of truth" rule. Meanwhile applications/conveyor-tasks/ defines only a namespace + ExternalSecrets, and that namespace is currently empty (the ES syncs fail, see C1).

Fix: Vendor the conveyor controller manifests (or its kustomization) into applications/ or core-components/ so ArgoCD owns it, or document the exception in an ADR if it's intentionally experimental.

High H3 — Liveness probes coupled to external dependencies amplify outages

linkding's liveness probe hits /health, which checks the database. DB down → kubelet kills the app → 9,962 restarts (and miniflux: 8,030; jellyseerr: 1,985; bazarr: 1,909). Restart storms burn CPU/IO on resource-constrained Pis and bury the actual signal. A liveness probe should answer "is this process wedged?", never "are my dependencies up?" — that's what readiness is for.

Fix: In applications/linkding/manifests/deployment.yaml (and peers), keep /health for readiness but switch liveness to a TCP socket check or a dependency-free endpoint. Add failureThreshold/longer periods to tolerate transient DB blips.

High H4 — Monitoring exists, alerting doesn't (effectively)

kube-prometheus-stack is healthy, yet cluster DNS was down for ~7 days, every ExternalSecret has been failing, and a CI listener crashlooped for 43 days — unnoticed (last repo activity 2026-04-19). Dashboards without routed, actionable alerts are decorative.

Fix: Route Alertmanager to something you read (ntfy/Telegram/email via ExternalSecret-stored credentials). The defaults (KubeDeploymentReplicasMismatch, KubePodCrashLooping, CoreDNSDown) would have caught all of this — they likely fired into the void. Add custom alerts for ExternalSecret SecretSyncedError and ArgoCD sync/health conditions.

5. Medium / Low Findings

Medium M1 — Kyverno mutate policy: 9× copy-pasted exclude list, Audit-mode findings ignored

applications/kyverno/manifests/mutate-image-registry.yaml repeats an identical 19-namespace exclude block in all 9 rules (575 lines; ~80 needed). Adding a namespace means editing 9 places — guaranteed future drift. Separately, validation policies run in Audit mode with 385 accumulated failures nobody triages — including the project's own workloads (e.g. jellyseerr fails the repo's own require-labels policy).

Fix: Label system namespaces (e.g. homelab/image-rewrite: disabled) and use a single namespaceSelector exclude, or YAML anchors per file. Triage the policy report: fix your own manifests' labels, then consider Enforce for new namespaces.

Medium M2 — ApplicationSets ignore image drift on every workload

Both appsets set ignoreDifferences on all container/init-container images (Deployments, StatefulSets, DaemonSets). This is a workaround for the Kyverno registry-rewrite mutation (autogen rules mutate pod controllers → permanent diff), but it means ArgoCD is blind to any image change — including a compromised or manually-edited image. The drift-detection value of GitOps is partially disabled cluster-wide.

Fix options: (a) write zot.mrcontainer.nl/... images directly in Git for your own manifests so no mutation/ignore is needed there, narrowing ignoreDifferences to chart apps only; or (b) disable Kyverno autogen for the mutate policy (pod-policies.kyverno.io/autogen-controllers: none) so only Pods (unmanaged by ArgoCD) are rewritten, then drop ignoreDifferences entirely.

Medium M3 — ArgoCD itself is not GitOps-managed (known TODO, aging)

ArgoCD was installed manually 347 days ago (raw manifests, --insecure flag); the repo only carries its cert/ingress. It's the one component whose version, config, and RBAC aren't reproducible from Git, and it's nearly a year old — multiple CVE-fixing releases behind.

Fix: Execute the documented TODO: argo-cd Helm chart in the core-components chart appset, values in Git (server.insecure: true stays, since TLS terminates at ingress). Document the bootstrap chicken-and-egg (ArgoCD managing itself) in an ADR.

Medium M4 — Namespace/destination mismatches in the manifest ApplicationSet

The git-generator templates destination.namespace: <dir-name>, but several components deploy elsewhere: media-server/ → namespace media, coredns/ and dnscrypt-proxy/ → kube-system. It works only because every manifest hardcodes its namespace, but it breaks the repo's stated "namespaces match the component name" convention and makes the Application's destination field misleading.

Fix: Rename media-server/ → media/ (or the namespace → media-server), and document kube-system-targeting components as exceptions in their READMEs.

Medium M5 — Single replicas everywhere on a 4-node cluster

Every app Deployment and all CNPG clusters run 1 replica; CoreDNS too (which is what made C1 a total outage instead of a partial one). Node4 already sits at 75% memory. For most homelab apps single-replica is a fine trade-off — but not for tier-0 (DNS) or stateful data (PG without backups, see C4).

Fix: Prioritize: CoreDNS ≥2 (with anti-affinity), CNPG instances: 2 for data you care about or backups (C4) — backups are cheaper on Pis. Leave stateless single-replica apps as-is.

Low L1 — Housekeeping

  • core-components/external-secrets/manifests/test-external-secret.yaml — a "test-secret" smoke test left permanently deployed (and now permanently red, polluting status).
  • Tailscale operator-oauth ExternalSecret refreshes every 1m (vs 1h elsewhere) — hammers AWS Secrets Manager API (cost/noise) for a credential that rarely changes.
  • Inconsistent manifest file naming: some components use numbered prefixes (00-, 01-), most don't.
  • ADR D16 (Talos migration) appears stale — cluster still runs k3s on Debian 353 days in; mark it rejected/deferred.
  • jellyseerr deployment lacks the app.kubernetes.io/name label its own Kyverno policy requires.
